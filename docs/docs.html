Relay documentation

Paystack, Flutterwave and Monnify each send all webhooks for an account to one URL, and Stripe sends every subscribed event to every endpoint. If several of your applications share that account, such as App A, App B and App C, you need something at that URL that works out which application each payment belongs to and passes the event on to it.

Relay is that piece. It receives your payment provider's webhooks, verifies them, decides which application owns each event, stores it safely and then delivers it to that application with its own signature. If an application is down, Relay retries for up to 24 hours. If no application, or more than one, can be identified as the owner, Relay holds the event for you to resolve. It never guesses and never broadcasts payment data.

  • One binary, no infrastructure. Embedded SQLite. No Redis, no message queue, no dashboard to host.
  • Safe by default. Signatures are verified on the exact bytes the provider sent. Relay answers the provider only after the event is committed to disk. Delivery is at least once, and recipients deduplicate on a stable event ID.
  • Language-agnostic. Your applications receive a plain signed HTTP POST, so no SDK is needed.
  • Paystack, Flutterwave, Monnify and Stripe. Enable any one, or several side by side. Each provider has its own endpoint: /webhooks/paystack, /webhooks/flutterwave, /webhooks/monnify or /webhooks/stripe. Most examples use Paystack; the Flutterwave, Monnify and Stripe sections cover what's different.
Relay does not process payments, hold money or replace checking a transaction with your payment provider.

How it works

                            ┌──────────────────────── Relay ─────────────────────────┐
 Paystack    ── webhook ──▶ │ verify signature ─▶ find owner ─▶ save to SQLite ─▶ 200 │
 Flutterwave ── webhook ──▶ │                                          │             │
 Monnify     ── webhook ──▶ │                                          │             │
 Stripe      ── webhook ──▶ │                                          │             │
                            │                         delivery workers ◀┘             │
                            └──────────────┬──────────────────┬────────────────────────┘
                                           ▼                  ▼
                                         App A              App B         (signed POSTs,
                                                                          retried on failure)
  1. The provider posts a webhook to Relay. Paystack posts to https://relay.example.com/webhooks/paystack, Flutterwave to https://relay.example.com/webhooks/flutterwave, Monnify to https://relay.example.com/webhooks/monnify, and Stripe to https://relay.example.com/webhooks/stripe.
  2. Relay checks the signature against the raw request body. For Paystack that's x-paystack-signature, made with your secret key. For Flutterwave it's flutterwave-signature or verif-hash, made with your secret hash. For Monnify it's monnify-signature, made with your client secret key. For Stripe it's Stripe-Signature, made with the endpoint's signing secret and timestamped against replays. Forged requests are rejected.
  3. Relay finds the owner. It looks at the transaction's reference prefix, its metadata, and any references or virtual accounts your applications registered through Relay's API.
  4. Relay saves the event and the decision in one database transaction, and only then answers the provider with 200.
  5. A background worker sends the event to the owning application and retries with backoff until it gets a 2xx.
What Relay foundStatusWhat happens
Exactly one owning applicationmatchedDelivered
No ownerunresolvedHeld. You add a rule, the app registers the reference, or you assign it (CLI, admin API or Go).
Conflicting ownersambiguousHeld. You decide (CLI, admin API or Go). See Operating Relay.

Relay currently routes these payment events:

  • Paystack: charge.success, both checkout payments and deposits into dedicated virtual accounts.
  • Flutterwave: charge.completed.
  • Monnify: SUCCESSFUL_TRANSACTION, both checkout payments and deposits into reserved accounts.
  • Stripe: checkout.session.* (completed, async payment succeeded/failed, expired) and payment_intent.* (succeeded, payment failed, processing, canceled).

Refunds, transfers, disputes and subscriptions are stored but not forwarded yet; see the FAQ. Customer IDs and emails are never used to decide ownership, because one customer can pay several of your applications.

Try it in five minutes

This runs Relay with two small demo applications on your machine and sends it a sample Paystack event. You need Docker, openssl and curl.

git clone https://github.com/khaleelhabeeb/relay.git
cd relay

Create the secrets file for the demo:

cat > examples/.env <<EOF
PAYSTACK_SECRET_KEY=sk_test_demo_only
APP_A_RELAY_SIGNING_SECRET=$(openssl rand -hex 32)
APP_A_RELAY_API_TOKEN=$(openssl rand -hex 32)
APP_B_RELAY_SIGNING_SECRET=$(openssl rand -hex 32)
APP_B_RELAY_API_TOKEN=$(openssl rand -hex 32)
EOF

Start Relay and the two demo applications, app_a and app_b:

docker compose -f examples/docker-compose.yml --env-file examples/.env up --build

In a second terminal, sign a sample payment the way Paystack would and send it. Its reference starts with APPA_, so it belongs to app_a:

PAYSTACK_SECRET_KEY=sk_test_demo_only examples/send-fixture.sh testdata/paystack/charge_success_checkout.json

You'll see the app_a container log the event with a verified signature. Send testdata/paystack/charge_success_metadata_object.json and app_b receives it instead, because its metadata says "application": "app_b".

Set up Relay for your applications

1. Describe your applications

Create relay.yaml. Each application needs a URL that Relay delivers to and its own signing secret. Secrets are never written in the file. Each *_env setting names an environment variable that holds the value.

server:
  listen: ":8080"                # webhooks from your providers (put HTTPS in front of this)
  api_listen: "127.0.0.1:8081"   # registration API and metrics, kept off the internet

storage:
  dsn: "/var/lib/relay/relay.db"

providers:                                    # enable one or more
  paystack:
    secret_env: PAYSTACK_SECRET_KEY           # your Paystack secret key (sk_live_… or sk_test_…)
  flutterwave:
    secret_hash_env: FLUTTERWAVE_SECRET_HASH  # the secret hash from Flutterwave's webhook settings
  monnify:
    secret_key_env: MONNIFY_SECRET_KEY        # your Monnify client secret key
  stripe:
    webhook_secret_envs: [STRIPE_WEBHOOK_SECRET]  # the Relay endpoint's signing secret (whsec_…)
    livemode: true                            # false for test mode

applications:
  app_a:
    endpoint: "https://app-a.yourdomain.com/webhooks/relay"
    signing_secret_env: APP_A_RELAY_SECRET   # Relay signs deliveries to this app with it
  app_b:
    endpoint: "https://app-b.yourdomain.com/webhooks/relay"
    signing_secret_env: APP_B_RELAY_SECRET
    registration_token_env: APP_B_RELAY_TOKEN  # optional: lets this app use the registration API
    payload_format: envelope                  # optional: wrap the provider's event in Relay metadata

routes:
  - application: app_a
    match:
      reference_prefix: "APPA_"
  - application: app_b
    match:
      metadata:
        app: "app_b"

Generate a secret for each application. Each must be at least 32 bytes and different from the others:

openssl rand -hex 32

Then check the file:

relay config validate -c relay.yaml

Validation reports every problem at once: a missing variable, an http:// endpoint, two routes that would both claim the same payment, and so on. Every option is listed in the configuration reference.

2. Tag each payment with its owner

When your application starts a transaction, include something Relay can recognise. Pick one approach per application. For Flutterwave, the reference is tx_ref and the metadata is meta, as shown in Flutterwave. For Monnify, they are paymentReference and metaData, as shown in Monnify. For Stripe, they are client_reference_id (or metadata.reference) and metadata, as shown in Stripe.

A reference prefix. Start every reference with the application's prefix:

curl https://api.paystack.co/transaction/initialize \
  -H "Authorization: Bearer $PAYSTACK_SECRET_KEY" -H "Content-Type: application/json" \
  -d '{"email":"parent@example.com","amount":500000,"reference":"APPA_INV_10293"}'

Metadata. Add a marker to the transaction's metadata:

{ "email": "buyer@example.com", "amount": 250000, "metadata": { "app": "app_b" } }

Registration. The application registers the reference, or (Paystack and Monnify) a dedicated virtual account, with Relay's API on the private api_listen address. This suits virtual-account deposits, whose references are generated by Paystack. See Registering ownership.

curl -X POST http://127.0.0.1:8081/v1/registrations \
  -H "Authorization: Bearer $APP_B_RELAY_TOKEN" \
  -d '{"provider":"paystack","type":"dedicated_account","bank":"Wema Bank","account_number":"9930000902"}'

If a webhook arrives before its registration, Relay holds it. It routes the event automatically as soon as the registration arrives, for events up to 72 hours old.

3. Accept Relay's deliveries in each application

Add an endpoint that does three things:

  1. Verifies the signature. See Verifying the signature.
  2. Ignores repeats. If you've already processed this X-Relay-Event-ID, return 200 and stop.
  3. Responds quickly with 2xx. Do slow work afterwards.

With payload_format: original (the default), the body is exactly what the provider sent. Your existing provider handling code keeps working, and only the signature check changes. The X-Relay-Provider header says which provider the event came from.

4. Run Relay behind HTTPS

export PAYSTACK_SECRET_KEY=sk_live_...          # if paystack is enabled
export FLUTTERWAVE_SECRET_HASH=...              # if flutterwave is enabled
export MONNIFY_SECRET_KEY=...                   # if monnify is enabled
export STRIPE_WEBHOOK_SECRET=whsec_...          # if stripe is enabled
export APP_A_RELAY_SECRET=...
export APP_B_RELAY_SECRET=...
export APP_B_RELAY_TOKEN=...
relay serve -c relay.yaml

Put a reverse proxy (Caddy, nginx, a cloud load balancer) in front of it to terminate TLS, and expose only the POST /webhooks/<provider> endpoints you use to the internet. There's a Docker setup in Running Relay in production.

5. Point your provider at Relay

Paystack: in the Paystack Dashboard, go to Settings → API Keys & Webhooks and set the webhook URL to your Relay address followed by /webhooks/paystack, for example https://relay.yourdomain.com/webhooks/paystack.

Flutterwave: in Settings → Webhooks, set the URL to https://relay.yourdomain.com/webhooks/flutterwave and the secret hash to the value of FLUTTERWAVE_SECRET_HASH, and turn on retries.

Monnify: in Developers → Webhook URLs, set the Transaction Completion URL to https://relay.yourdomain.com/webhooks/monnify. See Monnify.

Stripe: in Developers → Webhooks, add an endpoint at https://relay.yourdomain.com/webhooks/stripe for the routed events, and put its signing secret in STRIPE_WEBHOOK_SECRET. See Stripe.

Try it with your test keys first. Make a test payment for each application and confirm it arrives, and that nothing appears in relay events list --status unresolved. Before you switch live traffic, read Switching your provider to Relay.

Verifying the signature

  1. Read the raw request body. Don't parse and re-serialize it first.
  2. Reject the request if X-Relay-Timestamp is more than 5 minutes away from your clock.
  3. Build the signed message by concatenating these bytes: v1: + timestamp + : + event ID + : + delivery ID + : + raw body
  4. Compute the HMAC-SHA256 of that message with your application's signing secret, hex-encoded.
  5. X-Relay-Signature holds one or more comma-separated v1=<hex> values. During a secret rotation it holds two. Accept the request if any of them matches, comparing in constant time.

The event ID is part of the signed message. That stops anyone from replaying a captured request under a different event ID to get past your deduplication.

Python (FastAPI) 
import hashlib, hmac, time
from fastapi import FastAPI, Request, HTTPException

SECRET = b"..."  # RELAY signing secret for this app
app = FastAPI()

def relay_verified(headers, body: bytes, tolerance: int = 300) -> bool:
    ts = headers.get("x-relay-timestamp", "")
    if not ts.isdigit() or abs(time.time() - int(ts)) > tolerance:
        return False
    msg = f"v1:{ts}:{headers.get('x-relay-event-id', '')}:{headers.get('x-relay-delivery-id', '')}:".encode() + body
    expected = hmac.new(SECRET, msg, hashlib.sha256).hexdigest()
    return any(p.strip().startswith("v1=") and hmac.compare_digest(p.strip()[3:], expected)
               for p in headers.get("x-relay-signature", "").split(","))

PHP (Laravel) 
function relay_verified(string $secret, \Illuminate\Http\Request $request, int $tolerance = 300): bool
{
    $ts = (string) $request->header('X-Relay-Timestamp', '');
    if (!ctype_digit($ts) || abs(time() - (int) $ts) > $tolerance) {
        return false;
    }
    $message = 'v1:' . $ts . ':' . $request->header('X-Relay-Event-ID', '') . ':'
        . $request->header('X-Relay-Delivery-ID', '') . ':' . $request->getContent();
    $expected = hash_hmac('sha256', $message, $secret);
    foreach (explode(',', (string) $request->header('X-Relay-Signature', '')) as $part) {
        $part = trim($part);
        if (str_starts_with($part, 'v1=') && hash_equals($expected, substr($part, 3))) {
            return true;
        }
    }
    return false;
}

Node.js (Next.js route handler) 
import crypto from "node:crypto";

export function relayVerified(secret: string, headers: Headers, body: Buffer, toleranceSec = 300): boolean {
  const ts = headers.get("x-relay-timestamp") ?? "";
  if (!/^\d+$/.test(ts) || Math.abs(Date.now() / 1000 - Number(ts)) > toleranceSec) return false;
  const expected = crypto
    .createHmac("sha256", secret)
    .update(`v1:${ts}:${headers.get("x-relay-event-id") ?? ""}:${headers.get("x-relay-delivery-id") ?? ""}:`)
    .update(body)
    .digest();
  return (headers.get("x-relay-signature") ?? "").split(",").some((part) => {
    const p = part.trim();
    if (!p.startsWith("v1=")) return false;
    const got = Buffer.from(p.slice(3), "hex");
    return got.length === expected.length && crypto.timingSafeEqual(got, expected);
  });
}

// app/webhooks/relay/route.ts
export async function POST(req: Request) {
  const body = Buffer.from(await req.arrayBuffer());
  if (!relayVerified(process.env.RELAY_SIGNING_SECRET!, req.headers, body)) {
    return new Response("invalid signature", { status: 401 });
  }
  const eventId = req.headers.get("x-relay-event-id")!;
  // Deduplicate on eventId, verify with your provider, then fulfil.
  return new Response(null, { status: 204 });
}

Without the dependency:

func RelayVerified(secret string, h http.Header, body []byte, now time.Time) bool {
	ts := h.Get("X-Relay-Timestamp")
	sec, err := strconv.ParseInt(ts, 10, 64)
	if err != nil || now.Sub(time.Unix(sec, 0)).Abs() > 5*time.Minute {
		return false
	}
	m := hmac.New(sha256.New, []byte(secret))
	m.Write([]byte("v1:" + ts + ":" + h.Get("X-Relay-Event-ID") + ":" + h.Get("X-Relay-Delivery-ID") + ":"))
	m.Write(body)
	want := m.Sum(nil)
	for _, part := range strings.Split(h.Get("X-Relay-Signature"), ",") {
		if v, ok := strings.CutPrefix(strings.TrimSpace(part), "v1="); ok {
			if got, err := hex.DecodeString(v); err == nil && hmac.Equal(got, want) {
				return true
			}
		}
	}
	return false
}

Your application's responsibilities

  • Deduplicate on X-Relay-Event-ID. Delivery is at least once. A request can succeed at your end and still be retried, for example if Relay crashes before it records the result. Record the event ID in the same database transaction as the business effect. X-Relay-Delivery-ID and X-Relay-Attempt are for diagnostics only.
  • Respond quickly. Do slow work after you respond.
  • Verify the payment with your provider before granting value: check amount, currency, status and reference. A valid Relay signature proves the request came from Relay, not that the payment happened. Every application sharing a Paystack account holds its secret key, and anyone with that key can send Relay a correctly signed webhook. Relay then delivers it like any other. Setting confirm_with_api on the provider makes Relay check each payment with the provider's API before accepting it, but your own check is still the one that protects you.

Registering ownership

Static routes (reference prefix or metadata) cover most applications. When neither fits, for example with dedicated virtual accounts, an application can register identifiers through Relay's API with its own registration_token. The token alone decides which application the request acts for. The API listens on server.api_listen if you set it (recommended), otherwise on the main port.

RequestPurpose
POST /v1/registrationsClaim an identifier
GET /v1/registrations?type=&active=&limit=&after=List your own registrations, paginated (limit 1–500, follow next)
DELETE /v1/registrations/{id}Deactivate one of your registrations
# A transaction reference, before or after the payment ("provider" is paystack, flutterwave, monnify or stripe)
curl -X POST http://127.0.0.1:8081/v1/registrations \
  -H "Authorization: Bearer $APP_B_RELAY_TOKEN" \
  -d '{"provider":"paystack","type":"transaction_reference","value":"APPB_ORDER_1001"}'

# A dedicated virtual account (Paystack, or a Monnify reserved account; bank name and account number from the provider)
curl -X POST http://127.0.0.1:8081/v1/registrations \
  -H "Authorization: Bearer $APP_B_RELAY_TOKEN" \
  -d '{"provider":"paystack","type":"dedicated_account","bank":"Wema Bank","account_number":"9930000902"}'

curl -H "Authorization: Bearer $APP_B_RELAY_TOKEN" "http://127.0.0.1:8081/v1/registrations?type=dedicated_account"
curl -X DELETE -H "Authorization: Bearer $APP_B_RELAY_TOKEN" http://127.0.0.1:8081/v1/registrations/reg_01J...
ResponseMeaning
201Created. routed_events counts earlier unresolved webhooks that this registration just routed to you (see below for which).
200You already own it. Registering is idempotent.
409 registration_conflictAnother application owns it, or it falls under another application's reference_prefixes or a static route to another application.
401 / 422 / 429Bad token; invalid request (including a provider that isn't enabled, or dedicated_account for Flutterwave); or rate limited (10 requests per second per application, bursts of 20)

Registrations are kept separately per provider. A Paystack registration of a reference never claims a Flutterwave event with the same reference, and the reverse holds too.

Who can claim what:

  • Transaction references can never move to another application, even after deactivation. The original owner can claim them again.
  • Virtual accounts can move to another application only after the current owner deactivates them. Each deposit goes to whoever owned the account when it arrived.
  • A registration never overrides a static route or another application's namespace. A reference that starts with another application's reference_prefixes, or with a reference_prefix routed to another application, is refused with 409.
  • Reference namespaces. Give each application reference_prefixes so nobody else can register its references. An application that has them can only register references inside them, and gets 422 for anything else.
  • Webhooks that arrived first. A registration also routes matching unresolved webhooks that arrived before it. Inside the application's own reference_prefixes it picks up any from the last 72 hours. Anywhere else, including virtual accounts, it only picks up ones that arrived at most 15 minutes before the registration. Anything older stays unresolved for an operator to reroute.

Configuration reference

Relay reads one YAML file, set with --config. Unknown keys are rejected. Secrets never go in the file: each *_env field names an environment variable. relay config validate checks everything, including that those variables are set.

All options 
version: 1                      # optional; only 1 is supported

server:
  listen: ":8080"               # webhooks, /healthz, /readyz (and the API/metrics unless api_listen is set)
  api_listen: "127.0.0.1:8081"  # optional private listener for /v1/registrations, /v1/admin and /metrics
  admin_token_env: RELAY_ADMIN_TOKEN  # optional: enables the admin API on api_listen (32+ bytes, its own value)
  public_base_url: "https://relay.example.com"   # informational
  max_body_bytes: 1048576       # inbound webhook cap (default 1 MiB, max 16 MiB)
  max_concurrent_webhooks: 256  # webhooks processed at once; excess get 503 + Retry-After (the provider retries)
  metrics: false                # expose GET /metrics (Prometheus)
  trusted_proxies: []           # IPs/CIDRs of your reverse proxies (needed for allowed_ips behind a proxy)

storage:
  driver: sqlite                # only sqlite
  dsn: "/var/lib/relay/relay.db"  # local disk only; Relay creates the directory (0700) and file (0600)

providers:                      # at least one provider
  paystack:

  app_b:                         # application ID: lowercase letters, digits, _ or -
    endpoint: "https://app-b.yourdomain.com/webhooks/relay"
    signing_secret_env: APP_B_RELAY_SECRET            # required, ≥32 bytes, unique per app
    previous_signing_secret_env: APP_B_RELAY_SECRET_OLD  # optional, for rotation
    registration_token_env: APP_B_RELAY_TOKEN         # optional, ≥32 bytes, unique; enables the API
    reference_prefixes: ["APPB_"]  # optional: references only this app may register
    payload_format: original    # original (default) | envelope

routes:                         # static ownership rules
  - application: app_b
    provider: paystack          # optional: only events from this provider; omitted = every provider
    match:
      reference_prefix: "APPB_" # reference starts with this (case-sensitive): Paystack data.reference, Flutterwave data.tx_ref, Monnify paymentReference (accountReference for reserved accounts), Stripe client_reference_id or metadata.reference
      metadata:                 # every key equals its value (Paystack data.metadata; Flutterwave data.meta / meta_data; Monnify metaData; Stripe data.object.metadata)
        app: "app_b"             # both matchers set: both must match

delivery:
  max_attempts: 10              # per cycle; a manual retry starts a new cycle (1–50)
  timeout_seconds: 10           # per attempt (1–120)
  worker_count: 8               # concurrent deliveries (1–256)
  max_concurrent_per_application: 4  # workers one application may hold; default: all of them with one application, else half
  retry_schedule: [0s, 30s, 2m, 10m, 30m, 1h, 2h, 4h, 8h, 8h]  # delay before attempt N; last repeats; ±20% jitter
  allow_insecure_local: false   # DEVELOPMENT ONLY: allow http:// and private/loopback destinations

retention:
  payload_days: 90              # clear raw payloads this long after successful delivery (or dismissal)
  attempt_days: 90              # delete attempt history older than this
  held_days: 0                  # dismiss events still unresolved/ambiguous after this many days, with an alert (0 = never)

alerts:                         # optional: tell operators when something needs them (see Alerts)
  url_env: RELAY_ALERTS_URL     # enables alerts; the URL is read from this variable (Slack URLs are secrets)
  format: json                  # json (signed like deliveries) or slack
  secret_env: RELAY_ALERTS_SECRET  # required for json: signing secret, 32+ bytes
  digest_interval: 1m           # at most one digest this often (10s–1h)
  reminder_interval: 24h        # re-send a summary while anything needs attention; 0s turns reminders off

Validation rules

  • Applications: at least one is required. Signing secrets and registration tokens must each be at least 32 bytes and different for every application.
  • Endpoints: must use https, carry no credentials, and must not be localhost or a private IP. Relay also checks the resolved address every time it connects, which blocks DNS tricks. allow_insecure_local turns these checks off for local development only.
  • Routes: two routes to different applications are rejected if one always matches whenever the other does, for example prefixes APPA_ and APPA_ED_, or identical metadata matches. Overlaps that depend on the individual payment are caught at runtime, and the event becomes ambiguous. Routes scoped to different providers never overlap. A route's provider must be configured.
Rotating an application's signing secret
  1. Set previous_signing_secret_env to the current secret and signing_secret_env to the new one. Restart Relay. Each request now carries two v1= signatures.
  2. Deploy the new secret to the application. It accepts either signature in the meantime.
  3. Remove previous_signing_secret_env and restart again.
Restricting webhooks to your provider's IP addresses (optional)

Signature verification is what actually protects the endpoint. An allowlist adds defence in depth. Paystack publishes its webhook source IPs: 52.31.139.75, 52.49.173.169 and 52.214.14.220. Check Paystack's documentation for changes before relying on them.

providers:
  paystack:
    allowed_ips: ["52.31.139.75", "52.49.173.169", "52.214.14.220"]
server:
  trusted_proxies: ["10.0.0.0/8"]   # the addresses your reverse proxy connects from
  • Without trusted_proxies, the client is the direct TCP peer.
  • Behind a trusted proxy, Relay uses the rightmost X-Forwarded-For address that isn't itself a trusted proxy. It never trusts entries further left, because clients can forge them.
  • Rejected requests get 403.
  • Each provider has its own allowed_ips. Flutterwave says its IP addresses are dynamic, so leave providers.flutterwave.allowed_ips empty unless Flutterwave gives you a fixed list. Monnify publishes one address, 35.242.133.146, which you can put in providers.monnify.allowed_ips. Stripe publishes its webhook addresses at https://stripe.com/files/ips/ips_webhooks.txt; keep the list in sync if you use providers.stripe.allowed_ips.

Running Relay in production

docker build -t relay .
docker volume create relay-data
docker run -d --name relay --restart unless-stopped \
  -p 127.0.0.1:8080:8080 \
  --env-file /etc/relay/relay.env \
  -v /etc/relay/relay.yaml:/etc/relay/relay.yaml:ro \
  -v relay-data:/var/lib/relay \
  relay

The image is distroless, runs as a non-root user and keeps its data in the /var/lib/relay volume. Set storage.dsn: /var/lib/relay/relay.db in the config you mount.

  • Run one Relay per database. A lock file prevents a second instance. Keep the database on a local disk, not a network share.
  • Expose only the webhook endpoint. Terminate TLS at a reverse proxy, publish only the POST /webhooks/<provider> endpoints you use, and keep api_listen on a private interface.

Backups, upgrades and retention

  • Back up while Relay runs. The file contains payment events, so encrypt it: sqlite3 /var/lib/relay/relay.db "VACUUM INTO '/backups/relay-$(date +%F).db'"
  • Restore: stop Relay, put the backup in place as relay.db, delete relay.db-wal and relay.db-shm, then start Relay. To recover events received since the backup, resend them from your provider. Duplicates are ignored.
  • Upgrade: back up, stop the old version and start the new one. Schema migrations run on startup. Deliveries that were in flight are resumed first. Use the CLI from the same version as the server; it refuses a mismatched database.
  • Retention: every 6 hours Relay clears raw payloads of delivered and unsupported events older than retention.payload_days, and deletes attempt history older than retention.attempt_days. Payloads of events dismissed more than retention.payload_days ago are cleared too. Events that are unresolved, ambiguous, pending or exhausted keep their payloads until they're resolved. Set retention.held_days to dismiss events nobody resolves.
  • The database guide covers the schema, safe read-only queries, Litestream replication and the data lifecycle. Ready-made Prometheus alert rules are in examples/prometheus/relay-rules.yml.

Operating Relay

Events Relay can't give an owner are held: unresolved (no owner) or ambiguous (conflicting owners). So are deliveries that ran out of retries (exhausted) and events the provider's API couldn't confirm. Nothing is lost, but nothing is delivered either until someone acts. You can find and resolve all of them three ways, with the same rules and the same audit trail:

Way inBest for
The relay CLIAn operator at a terminal
The admin APIYour own admin panel, scripts and alerting, in any language
Go methods on *relay.RelayPrograms that embed Relay

You don't have to remember to look: alerts tell you when something needs you, and remind you until it's dealt with. Handling held events says what to do for each kind. You can also check relay stats (or GET /v1/admin/stats), or alert on the metrics.

The CLI

The relay CLI works against a running server. It only needs the config file, not the secrets.

TaskCommand

Every list and stats command accepts --json, which prints the same records as the admin API. relay events list returns 50 events by default (--limit up to 500); when there are more, it prints the --after value for the next page. To replay everything an application missed:

relay deliveries list --status exhausted --application app_b --json | jq -r '.data[].id' | xargs relay deliveries retry

When an event is unresolved, run relay events inspect to see its reference, metadata and the reason. Then do one of these:

  • add or fix a route, restart, and run relay events reprocess;
  • have the application register the identifier, which routes the event automatically;
  • assign the owner with relay events reroute;
  • if it belongs to none of your applications (a test payment, another business on the same account), close it with relay events dismiss. It keeps its history but stops counting as held. Rerouting it later still works.

When an event is ambiguous, two sources of evidence disagree. Fix the configuration so it can't happen again, then decide the owner with relay events reroute. Relay never changes the owner of an event that is already matched.

Admin API

The admin API does everything the CLI does, over HTTP, so you can build held events into your own admin panel or scripts. It's off until you give it a token:

server:
  api_listen: "127.0.0.1:8081"        # required: the admin API is never served on the public listener
  admin_token_env: RELAY_ADMIN_TOKEN  # at least 32 bytes, e.g. openssl rand -hex 32

The admin token is an operator credential. It must differ from every application's registration token and signing secret, and it can read payment payloads and reroute any event, so keep it out of your applications. Send it as Authorization: Bearer <token>.

Method and pathDoes
GET /v1/admin/statsHeld events, confirmations and deliveries by status, with the oldest of each
GET /v1/admin/eventsEvents, newest first. Filters: held=true (needing an owner decided), status, confirmation, type, provider, application, since (RFC 3339), limit (1–500, default 50), after (the previous page's next)
GET /v1/admin/events/{id}One event's routing history, deliveries, attempts and conflicting duplicates. ?include_payload=true adds the raw payment payload, and the read is logged.
POST /v1/admin/events/{id}/rerouteAssign an owner to a held event: {"application": "app_b", "reason": "ticket 42"}

  'http://127.0.0.1:8081/v1/admin/events?status=unresolved'

Errors use the same body as the registration API, {"error": {"code", "message"}}: unauthorized (401), not_found (404), validation_failed (422), invalid_state (409, e.g. rerouting an event that already has an owner or retrying a delivery that isn't exhausted) and admin_disabled (404, no admin token configured). Reroutes made through the API are recorded as operator decisions with the reason and via admin api.

Alerts

Relay can tell you when something needs you, so you don't have to poll. Each of these raises an alert once, when it happens:

AlertMeaning
event.unresolvedA payment arrived and no application owns it
event.ambiguousMore than one application claims a payment
delivery.exhaustedAn application missed an event: its retries are used up
confirmation.failedThe provider's API never confirmed an event, so it isn't delivered
confirmation.rejectedThe provider's API disowned a signed webhook: someone holding the secret may be forging events
dedup.conflictA duplicate webhook carried different ownership identifiers: possible forgery
event.expiredAn event was held longer than retention.held_days and was dismissed

Alerts are grouped into a digest, sent at most once per digest_interval (default 1 minute), so a misconfigured route doesn't flood you. Each digest lists up to 50 alerts, counts all of them, and includes the current totals. Alerts that no longer apply by the time the digest is built are left out. While anything still needs attention, a reminder with the totals goes out every reminder_interval (default 24 hours). Digests never contain payment payloads.

alerts:
  url_env: RELAY_ALERTS_URL   # a Slack incoming-webhook URL
  format: slack

Or send signed JSON to your own endpoint with format: json (the default) and secret_env. It's signed exactly like a delivery, with the digest ID as both X-Relay-Event-ID and X-Relay-Delivery-ID, so the same verification code (or receiver.Verify in Go) checks it. Its body is {"type": "relay.alerts", "id", "sent_at", "reminder", "counts", "alerts", "omitted", "stats"}.

Alerts are recorded in the same database transaction as the change they report, so a crash never loses one. If your endpoint is down, the same alerts are sent again at the next interval; they're kept for 7 days. Set retention.held_days to dismiss events nobody resolves, with a final event.expired alert. Embedded in Go, relay.WithAlertHandler receives the same digests.

Switching your provider to Relay

Changing the webhook URL moves every webhook for the account at once. Go step by step:

  1. Take inventory. List every system that handles the provider's webhooks today, and the event types each one relies on.
  2. Configure ownership. Give every application that takes payments a reference prefix, a metadata marker or registrations. Applications using dedicated virtual accounts must register their accounts.
  3. Update receivers. Each application verifies Relay's signature and deduplicates on X-Relay-Event-ID.
  4. Rehearse in test mode. Point your provider's test webhook URL at Relay. Make real test payments through each application, and confirm nothing shows up as unresolved or ambiguous.
  5. Plan for other event types. Refunds, transfers, disputes and subscriptions aren't forwarded yet. Make sure nothing depends on them, or keep handling them another way.
  6. Switch the live URL, then watch the unrouted and exhausted metrics closely for the first day.

The steps are the same for every provider. Use Flutterwave's test mode webhook settings or Monnify's sandbox for step 4. For Stripe, use a test-mode endpoint, or stripe listen.

Flutterwave

Relay handles Flutterwave webhooks the same way it handles Paystack's: verify, find the owner, store, deliver. Enable it alongside Paystack, or on its own:

providers:
  flutterwave:
    secret_hash_env: FLUTTERWAVE_SECRET_HASH

routes:
  - application: app_a
    match:
      reference_prefix: "APPA_"      # matches tx_ref; applies to both providers
  - provider: flutterwave
    application: app_b
    match:
      metadata:
        app: "app_b"                 # a key you set in the payment's meta
  1. In the Flutterwave dashboard, go to Settings → Webhooks. Set the URL to your Relay address followed by /webhooks/flutterwave, for example https://relay.yourdomain.com/webhooks/flutterwave.
  2. Set a secret hash there. Use a long random value (openssl rand -hex 32) and put the same value in FLUTTERWAVE_SECRET_HASH.
  3. Turn on webhook retries.
  4. Start each payment with a tx_ref that carries the application's prefix, or add a marker to its meta. Applications can also register a tx_ref with {"provider":"flutterwave","type":"transaction_reference","value":"..."}.

Signatureflutterwave-signature (base64 HMAC-SHA256 of the body) or verif-hash (the secret hash itself). Either one is accepted when it's valid.
Routed eventscharge.completed. Other events, such as transfer.completed, are stored as unsupported until their shape is checked against real payloads.
Referencedata.tx_ref, or data.reference for transfers
Metadatadata.meta, plus the top-level meta_data. Where both set a key, data.meta wins.
Duplicates<event>:<data.id>:<data.status>, as Flutterwave recommends. A failed charge followed by a successful one with the same ID counts as two events. Anything without an ID and status falls back to a SHA-256 of the body.

Tagging a Flutterwave payment with a reference prefix and a metadata marker:

curl https://api.flutterwave.com/v3/payments \
  -H "Authorization: Bearer $FLW_SECRET_KEY" -H "Content-Type: application/json" \
  -d '{"tx_ref":"APPA_INV_10293","amount":"5000","currency":"NGN","redirect_url":"https://app-a.yourdomain.com/paid","customer":{"email":"buyer@example.com"},"meta":{"app":"app_a"}}'

Monnify

Relay handles Monnify webhooks the same way as the others: verify, find the owner, store, deliver. Enable it alongside other providers, or on its own:

providers:
  monnify:
    secret_key_env: MONNIFY_SECRET_KEY
    confirm_with_api: true                # recommended when several applications share the account
    api_key_env: MONNIFY_API_KEY
    allowed_ips: ["35.242.133.146"]

routes:
  - application: app_a
    match:
      reference_prefix: "APPA_"      # matches paymentReference; applies to every provider
  - provider: monnify
    application: app_b
    match:
      metadata:
        app: "app_b"                 # a key you set in the transaction's metaData
  1. In the Monnify dashboard, go to Developers → Webhook URLs. Set Transaction Completion to your Relay address followed by /webhooks/monnify, for example https://relay.yourdomain.com/webhooks/monnify.
  2. Put the account's client secret key (Developers → API Keys & Contracts) in MONNIFY_SECRET_KEY. Monnify signs webhooks with it, and the same key authenticates the API.
  3. Start each payment with a paymentReference that carries the application's prefix, or add a marker to its metaData. Applications can also register a reference with {"provider":"monnify","type":"transaction_reference","value":"..."}.
  4. For reserved accounts, either give each account an accountReference that carries the application's prefix, or register the account once it's created: {"provider":"monnify","type":"dedicated_account","bank":"Wema bank","account_number":"..."}.

Signaturemonnify-signature: lowercase hex HMAC-SHA512 of the body, keyed with the client secret key. Monnify signs production webhooks only; see sandbox below.

Sandbox webhooks are unsigned. Monnify only sends monnify-signature in production, so by default Relay rejects every sandbox webhook with 401. To test against the sandbox, opt in:

providers:
  monnify:
    secret_key_env: MONNIFY_SECRET_KEY    # sandbox secret key
    api_key_env: MONNIFY_API_KEY          # sandbox API key (MK_TEST_...)
    confirm_with_api: true                # required
    api_base_url: "https://sandbox.monnify.com"   # required
    allow_unsigned_sandbox: true

With that set, an unsigned webhook is accepted only if it's a routed event type and Monnify's sandbox API confirms the transaction exactly. A webhook with a wrong signature is still rejected. Relay refuses to start if allow_unsigned_sandbox points at any API other than sandbox.monnify.com, and it logs a warning at startup whenever the option is on.

Trying it locally: sign a sample Monnify event and send it to a running Relay.

Stripe

Relay handles Stripe webhooks the same way as the others: verify, find the owner, store, deliver. Stripe lets you register several endpoints, but each one gets every subscribed event, so pointing each application at Stripe directly would broadcast every payment to all of them. Register one endpoint, at Relay:

providers:
  stripe:
    webhook_secret_envs: [STRIPE_WEBHOOK_SECRET]
    livemode: true                        # this Relay serves live events only
    confirm_with_api: true                # recommended when several applications share the account
    api_key_env: STRIPE_API_KEY           # restricted key with Events: read

routes:
  - application: app_a
    match:
      reference_prefix: "APPA_"      # matches client_reference_id or metadata.reference
  - provider: stripe
    application: app_b
    match:
      metadata:
        app: "app_b"                 # a key you set in the object's metadata
  1. In the Stripe Dashboard, go to Developers → Webhooks and add an endpoint at your Relay address followed by /webhooks/stripe. Subscribe it to the routed events below; others are accepted but only stored.
  2. Put the endpoint's signing secret (whsec_…) in STRIPE_WEBHOOK_SECRET. When you roll it, list the old and new secrets' variables in webhook_secret_envs until the old one expires.
  3. Tag each payment with its owner. On Checkout, set client_reference_id, and also payment_intent_data.metadata.reference to the same value so the PaymentIntent's events route too. On PaymentIntents, set metadata.reference or a marker key such as metadata.app. Applications can also register a reference with {"provider":"stripe","type":"transaction_reference","value":"..."}.
  4. For confirm_with_api, create a restricted key with read access to Events only. Relay refuses to start if its mode (rk_test_/rk_live_) doesn't match livemode.
Stripe
SignatureStripe-Signature: t=…,v1=…: hex HMAC-SHA256 of "<t>.<body>", keyed with the endpoint signing secret. Any v1 under any configured secret is accepted. A timestamp more than tolerance (default 5 minutes) from now is rejected.
Modelivemode must match the event's livemode; a mismatch gets 401. Run a separate Relay instance for test mode.
Routed eventscheckout.session.completed, checkout.session.async_payment_succeeded, checkout.session.async_payment_failed, checkout.session.expired, payment_intent.succeeded, payment_intent.payment_failed, payment_intent.processing, payment_intent.canceled. Charges, refunds, disputes, invoices and subscriptions are stored as unsupported for now.
Referenceclient_reference_id on a Checkout Session, otherwise metadata.reference
Metadatadata.object.metadata
ConnectEvents from connected accounts (top-level account) are stored as unsupported with type connect.<type>.
DuplicatesThe event id (evt_…)
ConfirmationWith confirm_with_api, Relay fetches GET /v1/events/:id. The type, livemode, and the object's id, reference, metadata, status, amounts and currency must match.

Use Relay as a Go library

relay serve is a thin wrapper around a Go package, so you can import Relay into your own program:

cfg, err := config.LoadFile("relay.yaml")              // or build a config.Config in Go
if err != nil { log.Fatal(err) }
r, err := relay.New(ctx, cfg, relay.WithLogger(slog.Default()))
if err != nil { log.Fatal(err) }
defer r.Close()

mux.Handle("/webhooks/", r.WebhookHandler())           // in your existing server
go r.Run(ctx)                                          // delivery and retention workers

// Claim a reference in-process when you create an order:
_, routed, err := r.RegisterReference(ctx, "billing", "paystack", "ORDER_1001")

// Find and resolve held events from your own code:
page, err := r.Events(ctx, admin.EventFilter{Status: admin.StatusUnresolved})
_, err = r.Reroute(ctx, page.Events[0].ID, "billing", "legacy order, ticket 42")

The operator methods Events, Event, Reroute, Reprocess, RetryConfirmation, Deliveries, RetryDelivery and Stats do what the CLI and the admin API do, with the same rules. Mount r.AdminHandler() on a private listener to serve the admin API yourself.

PackageUse it to
relayEmbed Relay: New, Handler/WebhookHandler/APIHandler/AdminHandler, Run/ListenAndServe, RegisterReference, and the operator methods
relay/adminThe records the operator methods, admin API and --json output share: Event, EventDetail, Delivery, Stats and the filters
relay/configLoad relay.yaml, or build and Validate a configuration in Go
relay/receiverVerify Relay's deliveries in a Go application (receiver.Handler)
relay/providerThe Adapter interface. Implement it and pass relay.WithProvider to add a payment provider.
relay/provider/paystack, relay/provider/flutterwave, relay/provider/monnify, relay/provider/stripeThe built-in adapters, also usable on their own

The full guide is in docs/library.md: embedding, configuration in Go, receiving deliveries, and writing a provider adapter. The API reference, with runnable examples, is on pkg.go.dev. To add a provider, implement provider.Adapter: verify the exact raw body in constant time, keep parsing free of secrets, return a stable dedup key, and route only event types you have checked against real payloads.

The API is pre-1.0 and may change between minor versions; CHANGELOG.md records every change.

FAQ

Does a delivery from Relay prove the customer paid?

It proves the event came from Relay, which verified that it came from your provider. Before giving value, check the amount, currency and status with the provider's Verify Transaction API, as you would without Relay.

Can my application receive the same event twice?

Yes. Delivery is at least once, so always deduplicate on X-Relay-Event-ID. Retries and replays keep the same ID.

What happens if Relay is down?

The provider gets no 200, so it retries.

  • Paystack retries every 3 minutes for the first 4 tries, then hourly for 72 hours in live mode.
  • Flutterwave retries only 3 times, 30 minutes apart, and only if retries are enabled in its dashboard.
  • Monnify resends when it gets no 200 or times out, on a schedule it doesn't publish.
  • Stripe retries with exponential backoff for up to 3 days in live mode (a few hours in test mode), and lets you resend events from the Dashboard.

Keep downtime short, especially with Flutterwave. Relay ignores anything that arrives twice.

What happens if my application is down?

Relay keeps retrying for about 24 hours by default, then marks the delivery exhausted for you to replay. Tune delivery.max_attempts and delivery.retry_schedule to change that.

Can I run several Relay instances for high availability?

Not on one database in this version. Relay is a single process with a lock file. The providers' own retries cover restarts and short outages.

Why aren't refunds, transfers or subscriptions forwarded?

Their payloads identify the owner differently, and Relay only routes event shapes that have been checked against real provider payloads. They're stored, so nothing is lost, and support is planned.

How are duplicate webhooks detected?

  • Paystack charge.success: by the transaction ID, so a resent event is recognised even if its bytes differ.
  • Flutterwave: by event:data.id:data.status, as Flutterwave recommends.
  • Monnify: by eventType:transactionReference:paymentStatus.
  • Stripe: by the event id (evt_…), which Stripe keeps across retries.
  • Anything else: by a SHA-256 hash of the exact body.
